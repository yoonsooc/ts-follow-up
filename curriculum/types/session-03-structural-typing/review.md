# Session 03 리뷰 — 구조적 타이핑의 이해 (interface 선언 병합 vs type)

**판정: ✅ 통과** (런타임 4/4, `tsc --noEmit` 통과 = `@ts-expect-error` 검증 충족)

## 잘한 것

- **`unique symbol` brand** — 강의안의 문자열 리터럴 brand(`__brand: "UserId"`)보다 강한 선택.
  `unique symbol`은 선언 위치마다 재현 불가능한 새 타입이 생기므로, 외부/타 라이브러리가
  우연히 같은 brand를 만들어 호환돼버리는 문자열 brand의 충돌 가능성 자체가 없다.
- 선언 병합으로 라이브러리 타입(`AnalyticsEvent`)을 소스 수정 없이 확장함
- Q1 정답: `type` 별칭은 같은 스코프에서 중복 선언 자체가 에러라 병합 불가
- Q2 유효: 타인이 필수 필드를 병합하면 기존 객체 리터럴들이 일제히 에러.
  (더 무서운 건 optional/호환 타입의 병합 — 에러 없이 계약이 조용히 바뀐다)

## 지적된 실수 (수정 완료)

1. **`as` 정당화 논리가 반대였음** — 최초 답변: "raw가 string이므로 UserId의 구조적
   요구사항을 만족하기 때문에 안전하다". 사실은 raw가 구조를 **만족하지 않는다**
   (`__brand` 없음). 만족했다면 `as`가 필요 없었을 것. 정당한 진짜 이유:
   ① brand는 런타임에 아무도 읽지 않는 가상 표식이라 거짓 주장이어도 깨질 코드가 없고,
   ② 그 거짓이 생성 함수(Rust newtype 생성자 격)라는 통제된 경계 한 곳에 격리되어 있기 때문.
   수정된 주석에서 두 세계(런타임/타입 장부) 구분까지 정확히 재서술함.

## 세션 중 나온 질문과 답 (추가 수확)

- **Q. `asUserId`에 string을 넣으면 반환값에 `__brand` 필드가 생기나?**
  아니다 — 런타임에서 `as`는 삭제되고 문자열이 그대로 나간다(`typeof uid === "string"`).
  `uid.__brand`를 읽으면 타입은 "있다"지만 런타임은 `undefined` — 타입과 런타임이
  어긋나는 지점이 존재하며, "아무도 brand를 읽지 않는다"는 규율 위에서만 안전하다.
  Rust의 `#[repr(transparent)] struct UserId(String)`(zero-cost newtype)과 같은 아이디어.

## 환경 변화 (이 세션에서 함께 처리)

- **TypeScript 7(tsgo) 업그레이드** — TS 7은 TS 5와 달리 `node_modules/@types`를
  자동 포함하지 않는다. `tsconfig.json`에 `"types": ["bun"]` 명시로 해결.
  (교훈: 컴파일러/도구 업그레이드 시 "코드가 아니라 설정" 기본값이 바뀔 수 있다)
- 퀴즈 원본 백업 `answer-origin.ts`는 의도적 미완성이라 tsc 게이트를 영구 실패시키므로
  `"exclude": ["**/answer-origin.ts"]`로 검사 제외.

## 기억할 원칙

- TS는 이름이 아니라 모양을 본다 (Go 인터페이스와 같은 철학, Java/Rust와 반대).
- 별명 타입(`type Id = string`)은 안전장치가 아니다 — 의미 구분이 필요하면 brand.
- 잉여 속성 검사는 "리터럴을 그 자리에서 넘길 때"만 작동한다. 변수 경유는 통과.
- 선언 병합은 "내가 소유하지 않은 타입 확장"에만. 내부 도메인 모델은 `type`으로 닫아라.
