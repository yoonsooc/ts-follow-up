대원칙: 두 세계는 분리되어 있다 Session 1

TS의 타입은 컴파일 후 전부 삭제된다. 타입 세계의 문법은 런타임에 아무 일도 하지 않는다.

세계존재하는 것지켜주는 것
타입 세계 (컴파일 타임)type, interface, as, 제네릭, brand코드 내부의 일관성
값의 세계 (런타임)객체, 함수, 클래스, Zod 스키마경계로 들어오는 실제 데이터

경계(fetch, JSON.parse, localStorage, env, 사용자 입력)에서 들어오는 값은 전부 unknown이다. 검증 없이 타입을 입히는 모든 수단(as T, return-only 제네릭, 표기+any)은 같은 거짓말이다.

📖 Handbook — The Basics (Erased Types)

any / unknown / never S1·S2

"모름"의 세 가지 표현 — 위험도는 하늘과 땅 차이.

any     // 검사 OFF. 모든 연산 허용 + 전염됨
unknown // 모든 연산 금지. narrowing 후에만 사용 가능
never   // 값이 존재할 수 없음. 분기 소진의 증거
// never로 exhaustiveness 강제 (Rust match 흉내)
default: {
  const _x: never = status; // 새 케이스 추가 시 컴파일 에러
  throw new Error(`unhandled: ${_x}`);
}
📖 any · unknown · Exhaustiveness

as — 단언과 방향 판정 S1·S2

캐스팅이 아니라 "검사하지 마라"는 무담보 약속. 런타임 no-op.

단언 전 → 후방향안전성
부분집합 → 상위집합넓히기항상 안전
같은 집합제자리무의미
상위집합 → 부분집합좁히기위험
  • 표기(: T)는 검사 요청, 단언(as T)은 검사 거부 — {} as Config는 컴파일되지만 const c: Config = {}는 에러
  • as unknown as X = Rust transmute — 무조건 반려
  • 정당한 좁히기: brand 생성 함수처럼 격리된 경계 한 곳뿐
📖 Type Assertions

리터럴 타입과 as const Session 2

값 하나가 곧 타입(집합 원소 1개). as const는 넓히기(widening)를 끄는 스위치.

const a = "PENDING";        // "PENDING" (좁게 유지)
let   b = "PENDING";        // string (넓혀짐)
const o = { s: "PENDING" }; // { s: string } — 값은 넓혀진다
const c = { s: "PENDING" } as const;
// { readonly s: "PENDING" } — 유일하게 항상 안전한 as
enum 대신: as const 객체 + 파생 유니언. enum은 런타임 코드를 생성하며(타입이 아니라 코드), TS 7 시대의 타입 스트리핑 도구와 마찰한다.
📖 Literal Types · Enums (비추천 이유 파악용)

typeof · keyof · T[K] Session 2

값 → 타입 파생의 3종 세트. "값을 선언하고 타입은 파생시킨다" (Go const 블록의 철학).

const OrderStatus = { Pending: "PENDING", Paid: "PAID" } as const;

typeof OrderStatus            // 값의 타입: { readonly Pending: "PENDING"; ... }
keyof typeof OrderStatus      // 키 유니언: "Pending" | "Paid"
(typeof OrderStatus)[keyof typeof OrderStatus]
                              // 값 유니언: "PENDING" | "PAID"

주의: 타입 문맥의 typeof(값→타입)와 런타임 연산자 typeof(값→문자열)는 다른 것. keyof는 as const 없이도 정확하다 — 넓혀지는 건 언제나 값.

📖 Typeof Types · Keyof Types · Indexed Access

Narrowing — typeof / in / 리터럴 비교 S1·S3

unknown을 쓸 수 있는 타입으로 좁히는 런타임 검사. 검사한 표현식 자체에만 적용된다.

if (typeof v === "string") { v.toUpperCase(); }   // 원시 타입
if (v !== null && typeof v === "object") { ... }  // null은 "object"! 별도 검사
if ("theme" in v) { v.theme }                     // 키 존재 → 프로퍼티 접근 가능
if (s === "dark" || s === "light") { ... }        // 리터럴 유니언까지 좁힘
함정: arr.length === 0 검사는 arr[0]을 좁히지 못한다. 컴파일러는 .length와 요소 존재의 상관관계를 모델링하지 않는다 — 값 자체를 검사하거나 for...of로 우회.
📖 Narrowing

Type Predicate — value is T S1·S4

반환 타입 자리의 타입 술어. 컴파일러는 본문을 검증하지 않고 서명을 그냥 믿는다 — 신뢰 지점.

function isConfig(v: unknown): v is Config {
  if (v === null || typeof v !== "object") return false;
  // 약한 단언: 값은 unknown 유지 → 검증 없는 사용은 컴파일 에러
  const { port } = v as { port?: unknown };
  return typeof port === "number";
}
  • 가드 안에서 as Config(강한 단언) 금지 — "검증 없는 사용"이 침묵으로 통과하게 됨
  • 가드는 throw하지 않는 총함수 — 거부(false)와 자폭(throw)은 다른 실패 모드
  • 잔여 위험: 타입-검증 드리프트 → Zod로 해결
📖 Type Predicates

interface vs type Session 3

체감되는 차이는 둘: 유니언/파생은 type만, 선언 병합은 interface만.

interface AnalyticsEvent { name: string }
interface AnalyticsEvent { ts?: number }
// 에러가 아니라 병합됨: { name: string; ts?: number }
상황선택
유니언 · 파생 · 조건부 타입type (interface 불가)
외부 공개, 소비자가 확장할 계약interface (병합 = 기능)
내부 도메인 모델type (의도치 않은 병합 원천 차단)

병합의 정당한 용도는 내가 소유하지 않은 타입 확장(Express Request, Window 등)뿐. optional 필드가 병합되면 에러 없이 계약이 조용히 바뀐다.

📖 type vs interface · Declaration Merging

구조적 타이핑과 Branded Type Session 3

TS는 이름이 아니라 모양을 본다 (Go 인터페이스 철학). 의미 구분이 필요하면 brand로 명목성을 흉내낸다.

type UserId  = string & { readonly __brand: unique symbol };
type OrderId = string & { readonly __brand: unique symbol };
// unique symbol은 선언마다 재현 불가능한 새 타입 → 서로 비호환

function asUserId(raw: string): UserId {
  return raw as UserId; // 격리된 의도적 단언 (Rust newtype 생성자 격)
}
  • type Id = string 별명은 안전장치가 아니다 — 그냥 string
  • brand는 런타임에 존재하지 않음 (zero-cost, repr(transparent) 격)
  • 잉여 속성 검사는 리터럴을 그 자리에서 넘길 때만 작동, 변수 경유는 통과
📖 Type Compatibility · unique symbol · Excess Property Checks

제네릭 — extends 제약과 절제 Session 4

존재 이유는 "두 위치의 타입 연결". 타입 파라미터는 시그니처에 두 번 이상 등장해야 한다.

// 정당: T와 K가 전부 2곳 이상에서 일한다
function pluck<T, K extends keyof T>(obj: T, key: K): T[K]

// 장식: 1회 등장 → (v: unknown)과 동일
function log<T>(v: T): void

// 흉기: return-only = as의 함수 포장
function parseJson<T>(text: string): T

사다리: 연산 불필요 → unknown / C의 연산 필요 → (v: C) / 구체 타입이 흘러감 → <T extends C>. TS 제네릭은 지워진다(단형화 없음): new T(), instanceof T 불가.

📖 Generics · Constraints

Record와 유틸리티 타입 Session 4

Record<K, V> = 키 K, 값 V인 객체. 키에 리터럴 유니언을 주면 데이터 차원의 exhaustiveness.

Record<string, number>       // Go map[string]int 격
Record<OrderStatus, string>  // 모든 상태 키 강제 — 누락 시 에러

Partial<T>  Required<T>  Readonly<T>
Pick<T, K>  Omit<T, K>   ReturnType<F>

제약/사전 타입에는 Record<string, any> 대신 Record<string, unknown> — 꺼낸 값마다 narrowing을 강제한다.

📖 Utility Types

Discriminated Union S2·S5

태그 필드로 구별되는 유니언 — Rust enum(sum type)의 진짜 TS 대응물.

type ConfigResult =
  | { ok: true;  config: AppConfig }
  | { ok: false; reason: string };

if (r.ok) { r.config } else { r.reason }
// 태그 검사로 variant가 좁혀짐 — 성공값과 실패값을 동시에 쥘 수 없다

switch + never default와 조합하면 variant 추가 시 컴파일 에러로 처리 누락을 잡는다.

Zod — 값의 세계의 방어선 Session 5

검증기에서 타입을 파생 → 타입-검증 드리프트가 구조적으로 불가능.

const S = z.object({
  theme: z.enum(["dark", "light"]),
  fontSize: z.number().int().min(8).max(32),
});
type Config = z.infer<typeof S>;  // 단일 진실 공급원

const r = S.safeParse(data);       // 절대 throw 안 함 (Result 격)
if (r.success) r.data; else r.error;
  • 경계에서 한 번 검증, 내부는 타입 신뢰 — 관세청이지 내부 검문소가 아니다
  • parse(throw)는 실패=버그인 지점(기동 시 env 등)에만

도구 규율 S1·S4

  • 실행기는 타입을 검사하지 않는다 — bun/esbuild/swc는 타입을 벗겨낼 뿐. 검사는 bunx tsc --noEmit으로 별도 강제 (CI 필수). 파일 인자를 주면 tsconfig가 무시된다(TS 7부터는 TS5112 에러로 알려줌).
  • 에디터의 빨간 줄도 하나의 검사기일 뿐 — VSCode 내장 tsserver(TS 5.x)와 프로젝트 TS 버전이 다를 수 있다. TS 7(tsgo)은 TypeScript Native Preview 확장으로 정렬.
  • @ts-expect-error — "다음 줄은 에러여야 한다". 에러가 안 나면 그 자체가 에러(TS2578) → 컴파일 타임 동작을 테스트하는 도구.
  • TS 7은 node_modules/@types를 자동 포함하지 않는다 → tsconfig에 "types": ["bun"] 명시.
